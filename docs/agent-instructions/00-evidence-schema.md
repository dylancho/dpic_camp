# 증거 파일 스키마 — `evidence.json`

이 문서는 조사 결과를 `evidence.json`으로 만들 때 지켜야 할 **출력 계약**이다.
블록별 지시서(`01-block-a-기술작동증명.md`, `02-block-b-해자.md`, `03-block-c-scaleup.md`)와
함께 읽는다. 이 문서 없이 블록 문서만 읽으면 항목 ID와 JSON 형식을 알 수 없다.

## 하지 않는 일

**점수를 세지 마라.** 몇 개 항목이 충족됐는지 계산하지 마라. 게이트를 통과했는지,
최종 합격·불합격인지 판정하지 마라. 그 작업은 이 레포의 파이썬 코드(`scoring.py`)가
결정론적으로 한다. 너의 역할은 항목별로 근거를 모으고 상태를 매기는 것까지다.

## 상태 판정 (`status`)

각 항목마다 다음 세 가지 중 하나를 매긴다.

- `MET` — 근거를 찾았고, 그 근거가 판정 기준(임계치)을 충족한다
- `NOT_MET` — 근거를 찾았으나, 그 근거가 판정 기준에 못 미친다
- `UNVERIFIABLE` — 판정할 근거 자체를 찾지 못했다

**`UNVERIFIABLE`과 `NOT_MET`을 혼동하지 마라.** 둘은 전혀 다른 정보다.
자료를 못 찾은 것(`UNVERIFIABLE`)과, 자료를 찾았는데 기준에 못 미치는 것(`NOT_MET`)을
같은 값으로 취급하면 안 된다. 특히 비상장 기업은 공시 의무가 없어 대부분의 항목에서
자료를 찾지 못하는 것이 정상이다 — 이때는 `NOT_MET`이 아니라 `UNVERIFIABLE`이 맞다.
근거 없이 추정하지 마라. 못 찾았으면 못 찾았다고 하는 것이 정답이다.

## 출처 등급 (`source_tier`)

근거가 실제로 어디서 나왔는지에 따라 1~4 중 하나를 매긴다.

| 등급 | 무엇 |
|---|---|
| 1 | DART 공시, 감사보고서 주석, 등록 특허 원문, 거래소 기술성 평가 |
| 2 | 제3자 공인 시험성적서, 독립 인증기관, peer-reviewed 논문 |
| 3 | 언론 보도, 산업 리포트 |
| 4 | 회사 자체 발표, IR 자료, 홈페이지 |

등급은 **근거가 실제로 어디서 왔는지만** 보고 매긴다. 그 출처가 얼마나 설득력 있는지,
항목을 충족시키기에 충분한지는 등급과 무관하다 — 언론 보도로 확인된 사실도 3급이고,
회사 홈페이지에 실린 정확한 수치도 4급이다. 출처가 무엇인지 분명하지 않으면 짐작해서
높여 적지 말고, 실제로 확인한 출처를 기준으로 매긴다.

**등급은 상태 판정에 영향을 주지 않는다.** 3급이든 4급이든, 판정 기준을 충족하는 사실이
확인되면 `MET`으로 매긴다. 등급을 이유로 `UNVERIFIABLE`로 낮추지 마라 — 등급은 그
판정이 무엇에 기대고 있는지를 기록하는 별도의 축이고, 하위 계층 코드가 그 구성을
집계해 결과에 함께 표시한다.

비상장 기업은 공개 자료가 대부분 언론 보도와 회사 발표뿐이라, 등급을 이유로 낮추면
어떤 회사도 서로 구분되지 않는다. **네가 할 일은 사실 관계를 정확히 판정하고 출처를
정직하게 기록하는 것**이지, 출처가 약하다는 이유로 판정을 유보하는 것이 아니다.

다만 **등급을 올려 적지는 마라.** 언론에서 읽은 것을 1급이라 적으면 결과를 읽는 사람이
근거의 성격을 오판한다. 실제로 본 출처 그대로 적는다.

## 항목 ID (`criterion_id`) — 전체 10개

아래 표에 없는 ID는 절대 만들지 마라. 이 표가 유일한 정답지다.
스키마에 없는 ID를 쓰면 해당 근거 전체가 조용히 버려지고, 그 항목은
`UNVERIFIABLE`로 남는다 — 실제로 자료를 찾았어도 못 찾은 것처럼 처리된다.

| `criterion_id` | 블록 | 항목명 | 지시서 |

| `B1_exchange_tech_grade` | B | 거래소 기술성 평가 | `02-block-b-해자.md` |

## `Evidence` 필드

한 근거(하나의 인용, 하나의 출처)마다 아래 객체 하나를 만든다.
한 항목에 근거가 여럿이면 `Evidence`도 여러 개 만든다 — 억지로 하나로 합치지 마라.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `criterion_id` | 문자열 | 예 | 위 표의 10개 값 중 정확히 하나 |
| `status` | 문자열 | 예 | `MET` / `NOT_MET` / `UNVERIFIABLE` 중 하나 |
| `source_tier` | 정수 (1~4) | 예 | 위 등급표 참고 |
| `source_url` | 문자열 또는 null | 아니오 | URL 또는 DART 접수번호. 조사에 쓴 모든 근거에 대해 기록할 것 |
| `quote` | 문자열 | 예 | 판단 근거가 된 **원문 인용**. 요약하거나 지어내지 마라 |
| `extracted_value` | 문자열 또는 null | 아니오 | PoC 건수·가동시간·특허 건수·석사 비중 등 정량값. 원문 표기 그대로 |

`UNVERIFIABLE`로 남기는 항목도 반드시 `Evidence`를 하나 만들어라 (`quote`에는 무엇을
찾아봤는지, `source_url`은 null로 두면 된다). 아무것도 안 만들면 "조사를 아예 안 한
항목"과 "조사했지만 못 찾은 항목"이 구분되지 않는다.

## 파일 형식

최상위는 `items` 키를 가진 객체이거나, `Evidence` 객체의 리스트 그 자체여야 한다.
둘 중 편한 쪽을 쓰면 된다.

```json
{
  "items": [
    {
      "criterion_id": "A2_third_party_validation",
      "status": "MET",
      "source_tier": 2,
      "source_url": "https://example-testlab.or.kr/report/2025-1234",
      "quote": "본 시험성적서는 OO공인시험기관이 2025년 3월 실시한 내구성 시험 결과이다.",
      "extracted_value": "2건 (2024-11, 2025-03)"
    },
    {
      "criterion_id": "B2_registered_patents",
      "status": "UNVERIFIABLE",
      "source_tier": 4,
      "source_url": null,
      "quote": "회사 홈페이지 '지적재산' 페이지에는 출원 중인 특허만 나열되어 있고 등록 여부가 명시되지 않음",
      "extracted_value": null
    }
  ]
}
```

이 예시는 실제 `Evidence` pydantic 모델로 검증했다 (아래 리포트의 검증 스니펫 참고).

## 조사 원칙

- 툴은 네가 가진 것을 쓴다 (웹 검색, 브라우징 등). 특정 제품의 툴 이름을 전제하지 않는다
- DART 공시를 볼 수 있으면 공시 원문(사업보고서, 감사보고서 주석)을 우선 확인한다.
  단, `B1`·`B2`·`B3`는 이 레포의 별도 규칙 추출기가 DART 공시에서 이미 일부를 뽑아둘 수
  있다 — 네가 추가로 찾은 근거와 중복되어도 괜찮다. 같은 항목에 대해 더 강한 근거
  (`MET`)가 있으면 그쪽이 채택된다
- 근거를 찾지 못한 항목도 빠뜨리지 말고 `UNVERIFIABLE`로 포함한다
- 게이트 통과 여부나 최종 합격·불합격을 판정하지 마라
